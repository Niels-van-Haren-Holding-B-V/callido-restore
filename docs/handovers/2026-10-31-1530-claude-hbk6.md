## The backup's own chunk table (Pool/chunk_index, hbk-1's #152)
`hbkgen.build(chunk_index=True)` / `--chunk-index` writes it from the generator's ground truth: 64-byte header (magic `7053a86e`),
one 29-byte record per chunk id at `64 + 29*g` = [0x00][u32 bucket][u32 64 + 32*entry][15 zero][u8 refcount][u32 fingerprint],
8 MiB slices. ASSUMED (the reader checks none of it): the rest of the header is zeros, a phantom id points at the entry of the
stored chunk it copies, unused or purged ids are all zeros, refcount = references from records, fingerprint = crc32(md5).
Off by default, so the other tests keep exercising the inferred map. `id_base_blocks=127` at scale 10 / 2 MiB uses id 289,260,
whose record straddles the first slice boundary (`truth.chunk_index_straddle`).
`ChunkIndexPath` (skipped until #152 is in): the E7 layout, rotation with the copy, the slice straddle, and under
HBK_E2E_STRESS the E5 layout: every run restores byte-exact, 0 errors, 0 unverified. With the table, E5 no longer
affects restores; it only matters for a backup that lacks the table.

## Sweep (after #118), every run restored against the manifest
Perfect whenever files span few buckets (scale ≤ 10 at 1 MiB, ≤ 20 at 2 MiB). Coverage depends on buckets per file, not size:
scale 20/1 MiB = scale 40/2 MiB = 29.8 %. Buckets under ~32 entries (≤ 256 KiB) are unrealistic (most tags straddle); ignore them.
0 wrong bytes in any layout.
